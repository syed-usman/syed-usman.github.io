---
title: "Why our load test kept failing at 170 users"
description: "A load test that kept failing at around 170 users, application logs that looked perfectly fine, and a load balancer that reset connections every time Kubernetes added a node."
date: 2026-10-28
---

We had to get a platform to 200 users at the same time. Every user gets their own JupyterLab server on Kubernetes, so 200 users means 200 pods and a few dozen new nodes coming up while people are still logging in.

The load test never got there. Every run stalled somewhere around 167 to 170 servers, and 15 to 23% of logins failed with TLS errors and connection resets. The annoying part was that the hub logs looked fine, and so did the ingress logs. As far as the application could tell nothing was wrong, because the failing connections never reached it.

When the app can't see a problem, reading the app logs harder doesn't help. So I gave myself one rule: every test run had to rule out at least one layer, with real evidence. Packet captures, counters, `kubectl`. No guessing.

## Ten runs

The first thing I found was a real bug. py-spy showed a blocking call inside the hub's event loop. I fixed it, and the failure rate didn't move at all.

After that I went down the stack. The ingress proxy, kernel connection tracking and the load-test client all came back clean. Switching to `externalTrafficPolicy: Local` helped a little but didn't fix it. A bigger load balancer changed nothing, so it wasn't capacity.

Then I pre-warmed the node pool before a run, and the failures halved. That was the clue. If adding nodes before the test helps, then adding nodes during the test is what hurts.

I also got one wrong along the way. Early on I was sure the auth provider was slow. My evidence was a `curl` timing, but that `curl` had hit a fast reject path, not the real login flow. I wrote it down in the investigation notes as a wrong call, so nobody would go chasing it again later.

## What was actually happening

Every time the autoscaler added a node, the cloud controller added that node to the load balancer's backend pool, and each of those updates reset the connections in flight. During a 200-user ramp the node pool grows almost constantly, so the load balancer was being reconfigured for the whole test.

The user nodes never needed ingress traffic in the first place. So the fix was to tag the user node pool and exclude it from the load balancer. If you try this, check how your provider handles tag values first. I learned that one the hard way.

With the resets gone, the next limit showed up straight away. The hub started rejecting spawns with HTTP 429, because its concurrent spawn limit defaults to 64. We raised it.

The final run had 200 of 200 servers up, zero failed logins and no hub restarts. On a confirmation run, 34 nodes joined during the test and the load balancer's backend pool didn't change once.

One more thing. The first time, I raised the spawn limit with a live patch, and the next Helm deploy quietly put it back. Both fixes live in Terraform and Helm now.

If I had to boil it down: when the app logs are clean and users are still failing, stop staring at the app. Look at where the connections die.
