Some platforms get their traffic in bursts. Think of a workshop, a class or an onboarding day: everyone opens the platform in the same minute, and everyone expects it to work the first time.

The platform in this story is one of those. It runs [JupyterHub](https://jupyter.org/hub), which gives every user their own JupyterLab server: a personal coding environment that runs as a pod on Kubernetes. When a user logs in, the hub starts their server. When 200 users log in at once, the hub starts 200 servers, and the cluster has to find room for all of them.

We needed it to handle 200 users starting at the same moment. In the staging load test it never got there. Every run stalled at around 167–170 servers, and 15–23% of logins failed with TLS EOFs and connection resets. In plain terms, the connection was closed before the user's browser got an answer.

This is how we found the cause, including the wrong turn, and what I'd check on any cluster that autoscales.

## How the pieces fit together

To follow the investigation you need the path a login takes:

1. The user's browser connects to a **cloud load balancer**, a managed service from the cloud provider that sits in front of the cluster.
2. The load balancer forwards the connection to one of the cluster's nodes. The set of nodes it can forward to is called its **backend pool**.
3. On that node, an **ingress proxy** receives the request and routes it to the hub.
4. The hub authenticates the user and asks Kubernetes to start their server.
5. The servers run on a separate **autoscaling node pool**. When it runs out of room, the cluster autoscaler adds nodes, and removes them again when they're idle.

On managed Kubernetes there is one more actor: the **cloud controller**. It keeps the load balancer's backend pool in sync with the cluster, so when a node joins, it gets added to the pool. Remember that one.

To generate the load we used [Locust](https://locust.io), which drove 200 simulated users through login and server start.

## The awkward part: the failures were invisible

The failing connections never reached the ingress proxy or the hub. The application logs looked healthy because, from the application's point of view, nothing had happened. Whatever was going wrong was happening below the app.

So the rule for the investigation was live evidence only: packet captures, logs and `kubectl`, no assumptions. Every run had to rule out at least one layer.

## Ten runs, one layer at a time

1. **The hub itself.** Profiling it with py-spy found a blocking call in the hub's event loop. That was a real bug and worth fixing, but fixing it didn't change the failure rate.
2. **Authentication.** Cleared. More on this one below.
3. **The ingress proxy, the kernel's connection tracking and the load-test client.** All cleared with packet captures and counters.
4. **`externalTrafficPolicy: Local`**, a setting that stops traffic hopping between nodes after it arrives. It helped, but didn't fix it.
5. **A bigger load balancer.** No change, so capacity wasn't the problem.
6. **Pre-warming the node pool**, adding the nodes before the test started. This halved the failures, and that was the clue. If adding nodes *before* the test helps, then adding nodes *during* the test is the problem.

## The wrong guess

Early on I concluded the auth provider was slow. My evidence was a `curl` timing, but that `curl` had hit a path that rejects requests quickly, not the real login flow. It was the wrong call. I wrote it down in the investigation log as a wrong call, so nobody would pick it up again later.

## The root cause

Each time the autoscaler added a node for user servers, the cloud controller added that node to the load balancer's backend pool. Each change to the pool reset connections that were in flight. During a 200-user ramp the node pool grows constantly, so the load balancer was being reconfigured throughout the test, and every reconfiguration dropped some logins.

The user-server nodes never needed ingress traffic in the first place. Only the nodes running the ingress proxy did. So the fix had two parts:

- **Keep the autoscaling user pool out of the load balancer's backend pool**, using a node-pool tag the cloud controller respects. Now nodes can come and go without the load balancer noticing. One detail I learned the hard way: check exactly how your provider reads tags before relying on them.
- **Raise the hub's limit on servers starting at once.** With the connection resets gone, the next bottleneck showed up: the hub was turning away server starts with HTTP 429 (too many requests). The Helm chart's default limit is 64 servers starting at the same time.

## The result

- **0 of 200** logins failed, down from 15–23%.
- **200 of 200** servers started, with zero failures and zero hub restarts.
- On a confirmation run, 34 nodes joined during the test and the load balancer's backend pool never changed.

## Make it stick

The first time, I raised the limit on server starts with a live patch. The next Helm deploy quietly reverted it. Since then, both fixes live in Terraform and Helm values, not in anyone's memory.

## What this means for you

If you run anything on Kubernetes behind a cloud load balancer, and your nodes autoscale, this can happen to you. Here's what I'd check:

- **Look at your load balancer's backend pool.** On many managed Kubernetes services it includes every node by default, including nodes that never serve ingress traffic. If nodes that autoscale are in that pool, every scale-up may be reconfiguring the load balancer under live traffic. Most providers have a label, tag or annotation to exclude a node pool. Find yours.
- **Load-test the cluster you'll actually have on the busy day.** A test against a warm cluster skips the part where nodes are being added, and that's exactly where this bug lived. Start from the node count you normally run with and let the autoscaler do its job during the test.
- **When application logs look clean, look below the application.** Check the load balancer's own metrics, take a packet capture on a node, and watch connection-tracking counters. The question is where the connection dies, not where the request is handled.
- **Treat "helped but didn't fix it" as a clue.** Pre-warming halved the failures, and that pointed straight at autoscaling.
- **Keep an investigation log, including the wrong guesses.** A wrong conclusion that isn't written down tends to come back in the next incident.
- **Read your Helm chart's concurrency defaults** before a big event: limits on concurrent starts, connections or requests. They are often set for an average day.
- **Put every fix in code.** A live patch is a countdown to the next deploy.
