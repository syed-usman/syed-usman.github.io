We needed a learning platform to handle 200 learners at once, each one starting their own JupyterLab server on Kubernetes. The staging load test never got there. Every run stalled at around 167–170 servers, and 15–23% of logins failed with TLS EOFs and connection resets.

This is how we found the cause, including the wrong turn.

## The setup

- JupyterHub on managed Kubernetes (Scaleway Kapsule), behind a Traefik ingress and a cloud load balancer
- An autoscaling node pool for user servers: every learner gets a pod, so 200 learners means dozens of new nodes
- Locust driving 200 simulated users through login and server spawn

## The awkward part: the failures were invisible

The failing connections never reached the ingress proxy or the hub. Application logs looked healthy because, from the application's point of view, nothing had happened. Whatever was going wrong was below the app.

So the rule for the investigation was: live evidence only. Packet captures, logs and `kubectl`, no assumptions. Every run had to rule out at least one layer.

## Ten runs, one layer at a time

1. **The hub itself.** Profiling with py-spy found a blocking synchronous call in the hub's event loop. A real bug, worth fixing, but fixing it didn't change the failure rate.
2. **Authentication.** Cleared. More on this one below.
3. **The ingress proxy, kernel connection tracking and the load-test client.** All cleared with captures and counters.
4. **`externalTrafficPolicy: Local`.** Helped, but didn't fix it.
5. **A bigger load balancer.** No change. Capacity wasn't the problem.
6. **Pre-warming the node pool.** This halved the failures, and that was the clue. If adding nodes *before* the test helps, then adding nodes *during* the test is the problem.

## The wrong guess

Early on I concluded the auth provider was slow. The evidence was a `curl` timing, and the `curl` had hit a fast-reject path, not the real login flow. It was a wrong call, and I wrote it down in the investigation log as one, so nobody would pick it up again later.

## The root cause

Each time the autoscaler added a user node, the cloud controller reconfigured the load balancer's backend pool to include it. Every reconfiguration reset connections that were in flight. During a 200-user ramp the node pool grows constantly, so the load balancer was effectively being reconfigured throughout the test.

The user nodes never needed to receive ingress traffic in the first place. The fix had two parts:

- **Exclude the autoscaling user pool from the ingress load balancer**, using a node-pool tag. One detail I learned the hard way: the provider rewrites tags that carry a value, so it had to be a bare key.
- **Raise the hub's concurrent-spawn limit.** With the connection resets gone, the next bottleneck was the hub rejecting spawns with HTTP 429. The chart default is 64.

## The result

- **0 of 200** logins failed, down from 15–23%
- **200 of 200** servers spawned, with zero spawn failures and zero hub restarts
- On a confirmation run, 34 user nodes joined during the test and the load balancer's backend pool never changed

## Make it stick

The first time, I raised the spawn limit with a live patch. The next Helm deploy quietly reverted it. Since then, both fixes live in Terraform and Helm values, not in anyone's memory.

One caveat stays documented: from a completely cold start the node pool still needs pre-warming before a big event.

## What I took from it

- **When application logs look clean, the problem is often below the application.** Look at where connections die, not where requests are handled.
- **Rule out one layer per run, and write each conclusion down**, including the wrong ones.
- **"Helped but didn't fix it" is a clue.** Pre-warming halving the failures pointed straight at autoscaling.
- **A fix that isn't in code isn't a fix.** It's a countdown to the next deploy.
